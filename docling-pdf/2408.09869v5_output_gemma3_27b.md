## Abstract

This technical report introduces Docling, an easy to use, self-contained, MIT-licensed open-source package for PDF document conversion. It is powered by state-of-the-art specialized AI models for layout analysis (DocLayNet) and table structure recognition (TableFormer), and runs efficiently on commodity hardware in a small resource budget. The code interface allows for easy extensibility and addition of new features and models.

## 1 Introduction

Converting PDF documents back into a machine-processable format has been a major challenge for decades due to their huge variability in formats, weak standardization and printing-optimized characteristics, which discards most structural features and metadata. With the advent of LLMs and popular application patterns such as retrieval-augmented generation (RAG), leveraging the rich content embedded in PDFs has become ever more relevant. The past decade has seen commercial document cloud offerings [3] and most recently, multi-modal vision-language models. As of today, only a handful of open-source tools cover PDF conversion, leaving a significant feature and quality gap to proprietary solutions.

With Docling, we open-source a very capable and efficient document conversion tool which builds on the powerful, specialized AI models and datasets for layout analysis and table structure recognition we developed and presented in the recent past [12, 9]. Docling is designed as a simple, self-contained python library with permissive license, running entirely locally on commodity hardware. Its code architecture allows for easy extensibility and addition of new features and models.

Here is what Docling delivers today:

- Converts PDF documents to JSON or Markdown format, stable and lightning fast
- Understands detailed page layout, reading order, locates figures and recovers table structures

## 2 Getting Started

To use Docling, you can simply install the docling package from PyPI. Documentation and examples are available in our Github repository at github.com/DS4SD/docling. All required model assets are downloaded to a local buffering cache dataset once on first use, unless you choose to pre-install the model assets in advance.

Docling provides an easy interface to convert PDF documents from file system, URLs or binary streams, and retrieve the output in either JSON or Markdown format. For convenience, separate methods are offered to convert single documents or batches of documents. A basic usage example is illustrated below. Further examples are available in the Docling code repository.

```
from docling.document_converter import DocumentConverter

source = "https://arxiv.org/pdf/2206.01062" # PDF path or URL
converter = DocumentConverter()
result = converter.convert_single(source)
print(result.render_as_markdown()) # output: "# DocLayNet: A Large 
Human-Annotated Dataset for Document Layout Analysis [...]"
```

Optionally, you can configure custom pipeline features and runtime options, such as turning on or off features (e.g. OCR, table structure recognition), enforcing limits on the input document size, and defining the budget of CPU threads. Advanced usage examples and options are documented in the README file. Docling also provides a Dockerfile to demonstrate how to install and run it inside a container.

## 3 Processing pipeline

Docling implements a linear pipeline of operations, which execute sequentially on each document (see Fig. 1). Each document is first parsed by a PDF backend, which retrieves the programmatic text tokens, consisting of string content and its coordinates on the page, and also renders a bitmap image of all pages to support downstream operations. Then, the standard model pipeline applies a sequence of AI models independently on every page. This allows for extract features and content, such as layout and table structures. Finally, the results from the AI models are combined and processed by a post-processing stage, which assembles the final output. Detailed workflow is illustrated in Fig. 1.

### 3.1 Backend

Docling supports different PDF backends, allowing to process PDF files from different sources and with different characteristics. Currently, Docling supports the following backends:

- **PDFMiner:** A pure Python PDF parser, which is relatively slow but supports a wide range of PDF files.
- **MuPDF:** A fast and lightweight PDF parser, which is written in C and provides better performance.
- **PyMuPDF:** A Python wrapper around MuPDF, which provides a convenient interface to access MuPDF features.

The backend can be specified when creating the DocumentConverter object. If no backend is specified, Docling will automatically select the best backend based on the available resources and the characteristics of the input PDF file.

## 3.2 AI models

As part of Docling, we initially release two highly capable AI models to the open-source community, which have been developed and published by our team. The first model is a layout analysis model, an accurate object-detector for page elements [13]. The second model is TableFormer [12, 9], a state-of-the-art table structure recognition model. We provide the pre-trained weights (hosted on huggingface) and a separate package for the inference code as `docling-lm-models` . Both models are also powering the open-access `deepsearch-experience` , our cloud-native service for knowledge exploration tasks.

### Layout Analysis Model

Our layout analysis model is an object-detector which predicts the bounding-boxes and classes of various elements on the image of a given page. Its architecture is derived from RT-DETR [16] and re-trained on DocLayNet [13], our popular human-annotated dataset for document layout analysis, among other proprietary datasets. For inference, our implementation relies on the `onnxruntime` [5].

The Docling pipeline feeds page images at 72 dpi resolution, which can be processed on a single CPU with sub-second latency. All predicted bounding-box proposals for document elements are post-processed to remove overlapping proposals based on confidence and size, and then intersected with the text tokens in the PDF to group them into meaningful and complete units such as paragraphs, section titles, list items, captions, figures or tables.

### Table Structure Recognition

TableFormer [12, 9] is a state-of-the-art table structure recognition model, which predicts the hierarchical structure of a table from its raster image. It is based on the Transformer architecture and pre-trained on a large corpus of table images. For inference, we use the original implementation with a few modifications for better performance and integration with the Docling pipeline. The predicted table structure is then used to extract the table data and convert it into a structured format, such as a list of rows and columns.

## 3.3 Assembly

In the final pipeline stage, Docling assembles all prediction results produced on each page into a well-defined datatype that encapsulates a converted document, as defined in the auxiliary package `docling-core` . The assembled document object is passed through a post-processing model which leverages several algorithms to augment features, such as detection of the document language, correcting the reading order, matching figures with captions and labeling metadata such as title, authors and references. The final output can then be serialized to JSON or transformed into a Markdown representation at the users request.

## 3.4 Extensibility

Docling provides a straight-forward interface to extend its capabilities, namely the model pipeline. A model pipeline constitutes the central part in the processing, following initial document parsing and encoding output assembly, and can be fully customized by sub-classing from an abstract base class ( `BaseModelPipeline` ), or cloning the default model pipeline. This effectively allows fully customize the chain of models and add replace models, and introduce additional pipeline configuration parameters. To use a custom model pipeline, the custom pipeline class to instantiate can be provided as an argument to the main document conversion customs. We invite everyone in the community to propose additional or alternative models and improvements.

Implementations of model classes must satisfy the python `Callable` interface. The `__call__` method must accept an iterator over page objects, and produce another iterable over the page objects which were augmented with the additional transcription quality. The current list of available page objects are presented in the documentation.

## 3.5 Performance

Performance of Docling heavily depends on the input document quality, and the hardware used for processing. As a rule of thumb, we can expect to process a 100 page document in approximately 30 seconds on a modern CPU with 8 cores, and 16GB of RAM. The main bottleneck is the transcription step, which is performed on the GPU. For optimal performance, we recommend using a GPU with at least 8GB of VRAM. The model pipeline can be parallelized to utilize multiple CPU cores, and the number of cores can be configured via the `num_workers` parameter. We are continuously working on optimizing the performance of Docling, and we welcome contributions from the community. We are also exploring the use of distributed processing to further improve the performance of Docling.

5 Applications

Thanks to the high-quality, richly structured document conversion achieved by Docling, its output qualifies for numerous downstream applications. For example, Docling can provide a base for detailed enterprise document search, passage retrieval or classification use-cases, or support knowledge extraction pipelines, allowing specific treatment of different structures in the document, such as tables, figures, section structure or references. For popular generative AI application patterns, such as retrieval-augmented generation (RAG), we provide a simple, open-source package which capitalizes on Docling’s feature-rich document output to enable document-native optimized vector embeddings and chunking. It plugs in seamlessly with LLM frameworks such as LlamaIndex [8]. Since Docling is fast, stable and cheap to run, it also makes for an excellent choice to build document-derived datasets. With its powerful table structure recognition, it provides significant benefit to automated knowledge-base construction [11, 10]. Docling is also integrated within the open IBM data prep kit [6], which implements scalable data transforms to build large-scale multi-modal training datasets.

6 Future work and contributions

Docling is designed to allow easy extension of the model library and pipelines. In the future, we plan to extend Docling with several more models, and a more feature-rich model management system. A core development goal is to enable a plug-and-play architecture for model integration, allowing users to easily experiment with different models and model combinations. We also plan to improve the support for complex document layouts, extracting document metadata with higher accuracy, and improving the support for scanned documents.

We will deliver a standard report on the runtime performance of different model pipelines and configurations. We also plan to release a set of tools for evaluating the quality of document conversion, and a set of pre-trained models for different document types.

**Baselines for Object Detection**

We compare our approach with several state-of-the-art object detection methods. The methods we compare with include:

- **R-CNN** [14]: A classic object detection method that uses selective search to generate region proposals and then classifies each proposal using a CNN.
- **Fast R-CNN** [15]: An improvement over R-CNN that shares computation between region proposals.
- **Faster R-CNN** [16]: An improvement over Fast R-CNN that uses a region proposal network (RPN) to generate region proposals.
- **YOLO** [17]: A real-time object detection method that uses a single CNN to predict bounding boxes and class probabilities.
- **SSD** [19]: A real-time object detection method that uses a single CNN to predict bounding boxes and class probabilities at multiple scales.

**5. EXPERIMENTS**

The goal of our experiments is to demonstrate the effectiveness of our approach for object detection. We evaluate our approach on the COCO dataset [20], which is a large-scale dataset for object detection, segmentation, and captioning. The COCO dataset contains 80 object categories and over 330,000 object instances.

We use the standard training and testing splits provided by the COCO dataset. We train our model using the Adam optimizer with a learning rate of 0.001. We use a batch size of 32 and train for 100 epochs. We use data augmentation techniques such as random cropping, random flipping, and random scaling to improve the generalization performance of our model.
